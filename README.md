# TGTranslate

Telegram-бот для изучения английского по статьям и книгам. Пользователь присылает ссылку или PDF,
из текста извлекаются слова, и по ним проходит квиз: слово, предложение из источника, где оно встретилось,
и 4 варианта перевода. Источник считается выученным, когда каждое слово угадано `CORRECT_TO_LEARN` (4) раза.

## Запуск

```bash
ollama pull qwen2.5:7b      # Ollama работает на хосте, модель нужно скачать один раз
cp .env.example .env        # впиши BOT_TOKEN от @BotFather и API_TOKEN (openssl rand -hex 32)
docker compose up --build
```

Ollama запускается на хосте (так он использует Metal/GPU), а контейнеры ходят в него по
`http://host.docker.internal:11434`. Другую модель можно задать через `OLLAMA_MODEL` в `.env`
(например `qwen2.5:3b` — быстрее, но хуже качество). На Linux Ollama на хосте должен слушать
не только localhost: `OLLAMA_HOST=0.0.0.0`.

Без Ollama: `TRANSLATOR=argos`, `pip install '.[argos]'` и установить языковой пакет en→ru
(`argostranslate.package`).

## Как это работает

```
bot ──HTTP──► api ──► Postgres
                 └──► Redis stream [source.submitted] ──► worker
                                                            │ httpx / pypdf → spaCy → Ollama
bot ◄── Redis stream [source.processed] ────────────────────┘
```

- `app/api` — FastAPI: приём источников, выдача вопросов, проверка ответов.
- `app/worker.py` — консьюмер очереди: загрузка, парсинг, лемматизация, перевод, запись в БД.
- `app/bot` — aiogram; уведомляет о готовности через `source.processed`.
- `app/messaging.py` — очередь на Redis Streams (consumer groups, подтверждение после обработки).
- Redis хранит очередь (с AOF, переживает перезапуск), открытый вопрос пользователя и последние
  `RECENT_WINDOW` заданных слов (чтобы слова не повторялись).
- Схему БД ведёт Alembic. В compose её накатывает одноразовый сервис `migrate`.

## Правила квиза

- Слова с наименьшим числом верных ответов идут первыми, но последние 10 заданных слов исключаются.
- Неверные варианты подбираются так, чтобы их нельзя было отгадать по части речи: сначала слова той же
  части речи из того же источника, потом из общего словаря, и только затем любые. Повторы и варианты,
  отличающиеся только регистром, отбрасываются.
- В вопросе показывается предложение из источника с выделенным словом и часть речи.
- `RESET_ON_WRONG=true` — считать 4 верных ответа подряд, а не суммарно.
- Под вопросом есть кнопки «⏭ Пропустить» (слово не засчитывается) и «⏹ Закончить» (прогресс сохраняется).
- Нижнее меню: «📚 Мои источники» и «❓ Помощь». В списке источник открывается карточкой с кнопками
  «▶️ Квиз», «🔄 Повторить» (для `failed`), «🗑 Удалить» (с подтверждением) и «⬅️ К списку».

## Безопасность и лимиты

- Ссылки: только `http(s)`, адрес должен быть публичным. Локальные, приватные, link-local (в том числе
  `169.254.169.254`) и зарезервированные адреса отклоняются. Проверка выполняется на каждом редиректе,
  а соединение идёт на уже проверенный IP (защита от DNS rebinding). Размер страницы — `MAX_PAGE_MB`,
  тип — только HTML/текст.
- PDF: сигнатура `%PDF-` и размер не больше `MAX_PDF_MB`; файл читается потоком, а не целиком в память.
- `ALLOW_PRIVATE_URLS=true` отключает проверку адресов. Только для локальной разработки.
- API доверяет `tg_id` из запроса, поэтому вызывать его может только бот: общий секрет `API_TOKEN` передаётся
  в заголовке `X-API-Token` (пустое значение отключает проверку, только для разработки). Порты API, Postgres
  и Redis в compose открыты только на `127.0.0.1`.
- `ALLOWED_TG_IDS` — список Telegram id через запятую, которым можно пользоваться ботом (пусто — всем).
- На одного пользователя не больше `MAX_ACTIVE_SOURCES` источников в обработке одновременно; повторная
  ссылка не обрабатывается заново. `/sources` показывает `SOURCES_PAGE_SIZE` последних источников.
- Пользователю показываются только «свои» причины ошибок (недоступный сайт, нет слов и т. п.);
  внутренние исключения пишутся в лог, а в чат уходит общее сообщение.
- Контейнеры работают не от root. Если том `uploads` создан старой версией образа, выдай пользователю `app`
  права на него или пересоздай том.

## Надёжность

- Пользователь получает уведомление «готово/ошибка» по меньшей мере один раз: источник помечается `notified`
  только после публикации события, а при повторной доставке сообщения событие отправляется заново.
  Временные сбои Telegram (сеть, 429) повторяются, а цикл уведомлений в боте перезапускается при ошибках Redis.
- Сообщение подтверждается только после обработки. Если воркер упал посреди источника, после
  перезапуска он получает то же сообщение снова и доделывает работу (все записи идемпотентны).
- Если API не смог поставить источник в очередь, он помечается `failed`, а пользователь получает ошибку.
  Источники, застрявшие в `pending` (падение между записью в БД и в очередь), воркер ставит в очередь при старте
  и затем каждые `STALE_PENDING_SECONDS`.
- Сбой перевода или загрузки помечает источник `failed` и отправляет пользователю причину. Провалившийся
  источник можно повторить или удалить кнопками в боте. Если обработка падает `MAX_ATTEMPTS` (3) раза подряд,
  воркер помечает источник `failed`, а не блокирует очередь. Битые сообщения пропускаются.
- После успешной обработки PDF удаляется с диска; у `failed` файл остаётся до повтора или удаления.
- Имена consumer'ов (`WORKER_CONSUMER`, `BOT_CONSUMER`) должны быть постоянными и уникальными для каждой
  реплики. Воркер и бот рассчитаны на одну реплику: два экземпляра с одним именем будут перехватывать
  необработанные сообщения друг у друга.

## Разработка

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e '.[dev]' && python -m spacy download en_core_web_sm
pytest                     # SQLite и fakeredis, ни Docker, ни сеть не нужны
TEST_DATABASE_URL=postgresql+asyncpg://user:pass@localhost/testdb pytest   # то же на настоящем Postgres
ruff check .
```

Миграции:

```bash
alembic upgrade head                                # применить (DATABASE_URL из .env)
alembic revision --autogenerate -m "what changed"   # после правки app/models.py
```

База, созданная старой версией через `create_all`, подхватывается первой же миграцией
(существующие таблицы пропускаются).

## Деплой на сервер (Docker + CI/CD)

Пуш в `main` → GitHub Actions прогоняет `ruff` и `pytest`, собирает образ, кладёт его в GHCR
(`ghcr.io/<owner>/<repo>:<sha>` и `:latest`), копирует `docker-compose.prod.yml` на сервер и делает
`docker compose pull && up -d`. Пайплайн — `.github/workflows/deploy.yml`.

В проде Ollama работает контейнером рядом с приложением (`ollama`), модели скачивает одноразовый
`ollama-pull` в том `ollama`. `qwen2.5:7b` на CPU требует ~8 ГБ RAM на сервере и переводит медленно;
на небольшом VPS ставь `OLLAMA_MODEL=qwen2.5:3b`. Бот работает через long polling, так что домен,
HTTPS и открытые порты не нужны — наружу контейнеры ничего не публикуют.

Сервер (один раз):

```bash
curl -fsSL https://get.docker.com | sh          # Docker + compose plugin
sudo systemctl enable --now docker              # Docker стартует после перезагрузки, контейнеры — за ним
sudo useradd -m -s /bin/bash deploy && sudo usermod -aG docker deploy
sudo -u deploy mkdir -p ~deploy/tgtranslate
# положи ~deploy/tgtranslate/.env по образцу .env.example: BOT_TOKEN, API_TOKEN, POSTGRES_PASSWORD
# добавь публичный ключ деплоя в ~deploy/.ssh/authorized_keys
```

GitHub → Settings → Secrets and variables → Actions:

| Secret | Значение |
|---|---|
| `SSH_HOST` | IP или домен сервера |
| `SSH_USER` | `deploy` |
| `SSH_KEY` | приватный ключ (`ssh-keygen -t ed25519 -f deploy_key -N ""`) |
| `SSH_PORT` | необязательно, по умолчанию 22 |

Необязательная переменная `DEPLOY_DIR` — каталог относительно домашнего у `SSH_USER` (по умолчанию `tgtranslate`).
Environment `production` можно защитить ручным подтверждением деплоя (Settings → Environments).

«Постоянно работает»: у всех сервисов `restart: unless-stopped`, поэтому упавший процесс перезапускается,
а после перезагрузки сервера Docker поднимает контейнеры сам. Логи ограничены 3×10 МБ на сервис.

На сервере вручную:

```bash
cd ~/tgtranslate
alias dc='docker compose --env-file .env --env-file .deploy.env'
dc ps                      # статус
dc logs -f bot worker      # логи
dc restart worker          # перезапуск сервиса
# откат: TAG=<старый sha> в .deploy.env, затем dc up -d
docker compose exec postgres pg_dump -U tgt tgt > backup.sql   # бэкап базы
```
